# v0.10.0 — SDK developer experience, React hooks and pnpm

## Scope and decisions

Preserve all 182 feature IDs, 41 scanner categories, 16 backend and 16 frontend suites. Add exactly one independently consumable package (`@saplings/hooks`) so the monorepo has 19 library packages. Existing `@sapling` names and `@saplings/validations` remain unchanged. The SDK is backend-only; never import it or secrets-bearing config into frontend bundles.

## API migration

`createSapling(config): SaplingSDK` constructs one SDK instance. Public getters return named, concrete service classes with emitted declarations; the registry is a private `#services` field and `expanded` is removed from the instance. This is an intentional pre-1.0 breaking change. Getters return the same service instances, not cloned wrappers; existing authorization, lifecycle, provider and persistence behavior is retained. All examples, CLI, worker, catalog tooling and regression consumers are migrated. `featureManifest()` exposes copies of the action inventory, not executable bindings.

Legacy config input `expanded` remains accepted for migration; the resolver normalizes it to `services` and rejects simultaneous definitions. There is no runtime `sdk.expanded` alias. `billing`, `jobs`, `identity`, `storage`, `access`, `realtime`, etc. are unchanged. Do not expose direct trusted backend methods to arbitrary HTTP clients: configured domain policies and the applicable service-level permission checks remain mandatory. Direct service methods do not universally apply the catalog feature gating policy.

## Type-safe catalog invocation

```ts
import {createSapling, defineSaplingConfig, type ActorContext, type FeatureId, type FeatureAction} from '@sapling/sdk';
const config = defineSaplingConfig({app:{id:'app',environment:'development'},services:{domainPolicies:{documents:{read:['title'],write:['title'],authorize:(ctx,action,row)=>ctx.actorId === row.ownerId && action === 'read'}}}});
const sapling = createSapling(config);
async function example(ctx: ActorContext) {
  const doc = await sapling.domains.get(ctx, 'documents', 'doc-1');
  const workflow = await sapling.providerWorkflows.start(ctx,'deploy','release-1',{}); // configured workflow required
  const result = await sapling.invokeCapability(ctx,'SAAS-001','register',{email:'user@example.com',password:'replace-at-runtime'});
  // result is unknown: validate provider-specific response before use.
  return {doc,workflow,result};
}
```

`FeatureId` is the union of all 182 identifiers. `FeatureAction<ID>` narrows actions to the registered set for that ID. `invokeCapability` enforces ID/action correlation at compile time, and invokes the existing runtime authorization and validation. The action inventory is generated by `catalog:refresh` and verified against runtime registrations. `capabilities.invoke` remains the dynamic escape hatch for discovered strings. Domain/provider payloads are still `JsonRecord` and provider results are `unknown`; compile-time schemas for every application-specific record are not implied. Runtime validation cannot be replaced with IDE completion.

## pnpm migration

- `pnpm-workspace.yaml` declares `packages/*`, `apps/*`, `examples/*`. Internal workspace dependencies use `workspace:*` and publish as normal versions through pnpm packaging. `packageManager` pins pnpm 10.11.0; Node >=22. `.npmrc` configures the shared lockfile, strict peers and engine checks.
- Root test/tool dependencies are explicit; production dependencies are separate. React is a peer of hooks, not a dependency of the Node SDK. Quality engine packages stay out of runtime deploy targets.
- CI uses pnpm setup, frozen installs once a lock exists, and a first-install review artifact otherwise. All Docker builds require a committed lockfile. Runtime examples use filtered production deployment (`pnpm deploy --legacy --prod`); quality runner retains dev tooling intentionally.
- Existing npm audit report support is retained; `pnpm-audit` evidence accepts advisory-shaped JSON and fails closed on malformed reports. Live audit output must be validated against the pinned pnpm release.

```bash
corepack enable
corepack prepare pnpm@10.11.0 --activate
pnpm install --no-frozen-lockfile # first time only; review and commit pnpm-lock.yaml
pnpm install --frozen-lockfile
pnpm run build:all
pnpm run typecheck:sdk
pnpm run typecheck:hooks
pnpm test
pnpm run test:hooks
pnpm --filter @sapling/example-express run dev
pnpm --filter @sapling/example-web run dev
pnpm run release:preflight
```

For external consumers after publishing the packages: `pnpm add @sapling/sdk` on the backend, `pnpm add @saplings/hooks react` in React applications. Do not use the workspace specifier in an external consumer. Run `pnpm pack` in the individual package to inspect output before publication. This archive contains source, not published packages.

## Verification and limits

The dependency-free core build, SDK type contract tests, local quality build and regression tests were run directly using globally available TypeScript and temporary workspace links. No fake pnpm executable or lockfile was created. Registry DNS failure prevented installing pnpm, React, upstream Zod, browser engines or cloud adapters. Hooks syntax/transpile checked; full React type check/build and runtime suite not executed. Existing live infrastructure and security gates remain open; two new gates track workspace-install and react-hooks. See evidence and release blockers.
