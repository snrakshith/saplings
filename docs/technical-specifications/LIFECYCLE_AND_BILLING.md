# Billing and tenant lifecycle — v0.8.0

## Recurring billing
`expanded/recurring.ts`, `registry.ts`, `worker.ts`. SAAS-036 `schedule`, `issueDue`, `cancelSchedule`; SAAS-048 `chargeDue`, `enqueue`, `sweep`. Configure `expanded.recurring.gateway` and `retryDays` in the trusted SDK config. Use a tenant scheduler to invoke bounded `sweep` (persist and rotate both returned cursors), or invoke issueDue for due subscriptions and enqueue an invoice-specific dunning job; call chargeDue when `nextAttemptAt` is due. This is fixed-day billing with snapshot price and currency; calendar proration, metered invoices, tax jurisdiction and actual mandate management remain application/provider responsibilities.

Data collections: `billing-schedules` (subscription ID), `invoices` (hash of schedule/period), `billing-attempts` (invoice ID). All monetary fields are integer minor units. The schedule/invoice write is one tenant transaction. Charge uses stable tenant/invoice/attempt key; an ambiguous outcome stays pending and reuses the same key. Verified decline creates the next retry after configured delay; exhausted attempts remain for review. A verified paid result closes the invoice and restores past-due subscription state. Payment gateway must deduplicate each key, check mandate/consent, amount/currency, reconcile authoritative provider events, and never treat order creation as payment. Concurrent provider retries are possible after the reservation delay; the idempotency contract is mandatory. Cancelled subscriptions are not charged on newly claimed attempts; in-flight payments need cancellation/refund reconciliation. No auto-debit provider is configured by default. Zero-amount invoices do not call a payment gateway.

## Tenant offboarding
`expanded/offboarding.ts`, SAAS-024 `request`, `approve`, `advance`, `status`. Explicit tenant confirmation, different requesting/approving actors, tenant transaction and step lease. Six ordered checkpoints: freeze, revoke, export, purge-external, purge-records, verify. Every configured callback receives a stable operation ID, must be idempotent and return evidence. On callback failure the step is not advanced; retry after lease expiry. Preserve the control records and append-only audit; legal hold, retention, external storage versions, identity broker tokens, billing agreements, worker termination, backups and regional replicas must be handled by actual application handlers. The registry freezes other capability calls as soon as offboarding is requested. The worker skips frozen tenants and recurring billing stops newly claimed charges and invoice issue. Already in-flight operations still require quiescence. It does not automatically guard raw store, direct typed service calls or all HTTP routes; implement and verify app-wide freeze/revocation and quiescence. A completed step represents supplied callback evidence, not proof of permanent deletion. Never delete audit/control records via generic purge. No hardcoded destructive default.

## Tests and release gates
Local tests verify concurrent single-period invoice creation, paid outcome, timeout key reuse, retry exhaustion, distinct offboarding approval, step progression and generic capability freeze. `recurring-payment-live` and `tenant-offboarding-drill` require approved sandbox/live evidence. Use test payment methods and a disposable tenant, never real customer funds or data. Document provider results, legal policy, deletion verification and remediation.
